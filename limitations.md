# Limitations & Follow-Up Risks

- **Unbounded growth of `providerLocks` and `appointmentsByProvider`.** Every distinct `providerId` ever seen gets a permanent entry in both maps, with no eviction. Fine for a bounded assessment run; a long-running real service would need either a bounded cache with eviction or a different locking primitive (e.g., striped locks) to avoid unbounded memory growth under high provider cardinality.
- **Pure in-memory store.** All appointments are lost on restart — no persistence, no write-ahead log, no recovery. Acceptable here since durability was explicitly out of scope; a production version would need a real datastore that preserves the same overlap-safety guarantee under concurrent transactions.
- **No pagination on `GET /appointments/{providerId}`.** It returns every appointment (active and cancelled) for a provider in one response. Fine at manual-smoke-test scale; a provider with years of history would need paging or a date-range filter.
- **No retention/cleanup of cancelled appointments.** `CANCELLED` appointments stay in both the id-index and the provider's list forever — a provider who books and cancels repeatedly accumulates an ever-growing list with no way to prune it. Same root cause as the lock-map growth above, just on the data side.
- **Per-provider locking only guarantees correctness within one process.** The whole concurrency story (`computeIfAbsent`-created locks, `book`/`cancel` sharing a lock) lives in one JVM's memory. It gives no safety at all if this were horizontally scaled to multiple instances behind a load balancer — each instance would have its own independent lock map and store, and two instances could both "win" the same slot. Not a concern for this single-process assessment, but it's the first thing that would need to change (DB-level locking/transactions, or a distributed lock) before running more than one instance.
- **`GET /appointments/{providerId}` isn't sorted by time** — it returns appointments in booking (insertion) order, not chronological order. Minor, but worth naming since this endpoint's whole purpose is manual eyeballing of a provider's schedule, and an unsorted list is mildly confusing for exactly that use case.
- **The malformed-JSON handler (`HttpMessageNotReadableException` in `AppointmentController`) has no dedicated test.** It was added and manually verified against the running server during a later fix, but no regression test was added for it — flagged during self-review and still open. If that handler were accidentally removed or broken in a refactor, nothing in the suite would catch it.
